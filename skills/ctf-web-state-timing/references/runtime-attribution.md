# 计时异常的运行环境归因

在“客户端观察的延迟”与“源码规定的延迟”不一致时使用。先记录两条观察各自的来源、单位、版本、采样范围；不要为了得到单一原因而删掉无法解释的数据。

## 最小观测集

- 客户端：请求顺序、实际并发、连接复用、前缀长度与编码、状态码、超时、代理/重试配置、响应头完成时间及完整正文耗时。保留原始样本与对照；Requests 的 `Response.elapsed` 结束于响应头解析完成，不是完整正文耗时，也不要改称严格的首字节时间。[Requests 文档](https://requests.readthedocs.io/en/latest/api/#requests.Response.elapsed)
  只有若干均值/中位数或“每字符延迟”点估计，不能证明测量分辨率、噪声水平、信号显著性或控制器可靠性；还需原始分布、样本量、测量定义、对照与重复测量。点估计接近源码参数只支持数值接近，不等于仪器或链路已经校准。
- 自有或已授权本地实例：固定服务端源码、依赖文件/二进制 SHA-256、镜像 ID/digest、操作系统、启动参数和 worker 数；只提取需要的字段，避免完整输出环境变量或容器配置中的凭据。标注 CPU 配额、CPU 亲和性及 cgroup 层级，线程数不代表 CPU 配额。
- 仅在有服务端访问权限时，在同一采样窗口读取服务进程对应 cgroup 的 `cpu.max` 与前后两次 `cpu.stat`，比较 `nr_throttled`/`throttled_usec` 增量。同时检查可见祖先约束；某些节流统计不包含祖先施加的限制。缺文件或控制器未启用记为“不可观测”，不是零节流。`cpu.max` 的 quota/period 与 `cpu.stat` 时间字段单位依内核文档解释。[Linux cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files)
- 可以修改自有测试服务时，分开记录函数执行的单调墙钟时间和进程/线程 CPU 时间。等待会增长墙钟时间而未必增加 CPU 时间。服务端指标与客户端请求须能对齐；一次节流增量与一次慢请求同时出现还不是充分的因果证据。

## 可区分实验与结论上限

| 假设 | 能增加区分度的材料/实验 | 单凭这些不能下结论 |
|---|---|---|
| 部署代码或依赖不同 | 实际部署文件哈希/镜像/构建记录；固定资源时对比两个构建 | 官方仓库与客户端斜率不一致 |
| CPU 配额或调度等待 | 同窗口节流/压力指标；相同构建仅改变资源条件，观察是否可重复 | 增加客户端线程数、单次本地 sleep 校准、只有本机 cgroup 指标 |
| 代理重试、队列或连接开销 | 服务端请求 ID/次数、访问日志、分阶段计时；本地控制一个因素 | 把全程耗时全部归入比较函数 |

假设不必二选一，也可能同时成立。当前本地环境的结果不能恢复历史服务端状态；拿不到当时的部署与遥测时，交付“差异已观察，来源未定”，列出缺失材料并停止用不可区分的重复实验强化猜测。对照实验在自有本地服务中进行。
